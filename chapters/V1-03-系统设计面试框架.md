# 第一卷第 3 章：系统设计面试框架

## 学习目标与原文对齐

对应理解问题、提出高层设计、深入设计、总结四步。目标：能组织一场设计讨论，先澄清再选方案，并在时间内讲清取舍。先修 V1-01、02。

## P0 交互一：可分支的面试练习

- 初始题目：“设计一个短网址服务”；先隐藏架构答案，显示面试官、候选人和需求记录板。
- 操作：从问题卡选择或自行写入澄清问题；固定题库按功能、规模、延迟、可用性、保留时间给出预设回答；未知问题进入“自行假设”记录，不编造面试官事实。
- 样例分支：选择“需要点击统计”后需求板增加分析链路；选择“链接不可修改”与“允许修改”分别触发重定向缓存讨论。
- 反馈：标出已确认、仍是假设、超出范围的条目；用户跳过澄清直接画图时显示未覆盖需求，而不禁止继续。
- 下一步：用户选高层组件并说明目的，再揭示一份可行参考方案，逐项比较需求覆盖，而非检查图形是否完全一致。

## P1 交互二：时间与深入方向训练

- 参数：总时长 30/45/60 分钟；45 分钟默认建议分配 7/10/20/8 分钟，可修改。
- 操作：拖动四个阶段的时间预算；练习时可暂停，在“还有 8 分钟”时抽取一个追问，例如热点链接或存储增长，选择深入的模块。
- 反馈：显示当前设计最大未解决风险、选定深入方向的理由和总结遗漏项。计时结束仍允许完成，不用倒计时惩罚初学者。
- 复盘：生成需求—决策—证据—未解决问题的文字大纲；不依赖 AI 才能生成。

## 思维导图

- 澄清 → 功能、规模、非功能、范围排除、假设。
- 高层设计 → API、数据模型、主流程、获得共识。
- 深入 → 瓶颈、取舍、故障、估算验证。
- 总结 → 回顾需求、限制、扩展、监控。
- 沟通 → 提问、解释原因、回应反馈、时间管理。

各阶段节点可跳回练习对应记录；“需求影响决策”连到短网址分支。

## 额外学习内容与练习

提供两段原创回答对照：一段只报技术名词，一段说明需求和选择原因。让用户标出后者的信息增量。增加 90 秒开场、5 分钟架构讲解和 60 秒总结卡。

1. 排序题：澄清、估算、高层设计、深入、总结如何衔接？要点：可迭代，不要求机械线性。
2. 判断题：“一开始选好数据库能体现经验。”要点：应先知道数据与访问需求。
3. 场景题：剩 8 分钟，主流程还缺失败路径，是否继续介绍新组件？要点：优先补关键风险并总结。
4. 开放题：写三条能改变架构的澄清问题，说明各自影响。

## 验收与边界

至少两种不同需求分支能导向合理的不同设计；自定义答案保留原文；评分依据需求和逻辑，不声称存在唯一标准答案。框架章以决策流程与表达训练为主，不制造无教学目的的请求动画。
