# 第一卷第 1 章：从零到百万用户

## 学习目标与原文对齐

对应原文的单服务器、数据库、负载均衡、复制、缓存、CDN、无状态 Web 层、数据中心、消息队列、数据库扩展。目标：能追踪一次请求，并根据具体瓶颈解释为什么增加一个组件。先修：HTTP、数据库读写；后续关联 V1-02、05、06。

## P0 交互一：架构逐级生长

- 画面：客户端、DNS、Web、数据库的初始图；右侧显示请求事件、各层处理次数和瓶颈说明。
- 操作：从单机开始，依次选择拆数据库、增加负载均衡和 Web 副本、加入缓存/CDN、外置会话、队列、数据库分片；每一步先选“当前要解决的问题”。
- 参数：请求量 10—1000 次/模拟秒、读比例 0—100%、缓存命中率 0—100%、Web 副本 1—4。教学假设单 Web 容量 100 次/秒、数据库 80 次/秒，均可查看，不当作真实容量。
- 样例：100 次/秒、80% 读、缓存读命中率 75%；无缓存数据库承接 100 次，有缓存承接 20 次未命中读和 20 次写，共 40 次。明确只计算数据库访问次数，忽略回填额外操作。
- 反馈：同一请求在不同阶段走不同路径；增加 Web 后数据库仍过载时，提示剩余瓶颈。点 CDN 只高亮静态资源请求，不把所有动态请求都缓存。
- 结束任务：用三句话说明本次增加的组件、解决的问题和新增代价。

## P1 交互二：扩容后为什么掉登录

- 初始：两个 Web 节点，会话只存在 A；用户登录后下一请求被分到 B。
- 操作：切换本地会话、粘性会话、共享会话存储；停掉 A，再重试同一请求；随后开启读副本并设置 0—5 步复制延迟。
- 反馈：显示“请求到达哪个节点、是否找到会话”；数据库面板展示主库与副本版本，更新后立即读副本可以看见旧值。引导比较提高读吞吐与读取新鲜度的关系。
- 恢复：A 恢复不应自动让所有失效会话复活；各方案的会话有效期假设单独列出。

## 思维导图

- 请求入口 → DNS、HTTP、负载均衡。
- 计算扩展 → 垂直/水平扩展、无状态服务、会话外置。
- 数据层 → SQL/NoSQL 的场景、读副本、分片、热点。
- 加速 → 缓存命中与失效、CDN、数据新鲜度。
- 异步与可靠性 → 队列、重试、多数据中心、故障恢复。
- 运维与演进 → 日志、指标、自动化、由瓶颈驱动。

## 额外学习内容与练习

增加“一个请求的旅行”分镜和缓存/复制/分片三者对比图。架构补全题隐藏负载均衡与共享会话，让用户按需求补入。

1. 预测题：上述缓存样例数据库承接多少次访问？答案要点：40 次/秒，读写分别计算。
2. 诊断题：Web 已扩为四台，数据库排队仍增长，继续加 Web 有何问题？要点：瓶颈未解除。
3. 取舍题：所有读取都走副本是否合适？要点：说明复制延迟与读己之写要求。
4. 复述题：从单机到多机，挑三个必要改变，逐一给出触发条件。

## 验收与边界

正常、缓存未命中、Web 故障、陈旧读取均可单步复现；请求量不被等同为用户总数；架构不会因“百万用户”标签自动要求微服务或分库。导图能定位两个实验，简化指标均有计算口径。
